gfx1250 / WMMA worked example for ds_load_tr16.b128
Generated by instrumenting lowerDsReadTr() in
third_party/amd/lib/TritonAMDGPUToLLVM/MemoryOpToLLVM.cpp with LinearLayout::toString()
dumps and running triton-opt on the reproducer below (no GPU required -- lit-test style).

Reproducer (saved as blog_example.mlir, repo root):

  #mma_b16 = #ttg.amd_wmma<{version = 3, ctaLayout = {warp = [[0, 1], [1, 0]]}, instrShape = [16, 16, 32]}>
  #shared1 = #ttg.swizzled_shared<{vec = 1, perPhase = 1, maxPhase = 1, order = [1, 0]}>
  #smem = #ttg.shared_memory

  tt.func @blog_example(%arg1: !ttg.memdesc<64x128xf16, #shared1, #smem, mutable>, ...) {
    %2 = ttg.local_load %arg1 : !ttg.memdesc<64x128xf16, #shared1, #smem, mutable>
           -> tensor<64x128xf16, #ttg.dot_op<{opIdx = 1, parent = #mma_b16, kWidth = 8}>>
    ...
  }

Run with:
  triton-opt blog_example.mlir --convert-triton-amdgpu-to-llvm=gfx-arch=gfx1250 --convert-builtin-func-to-llvm

Setup: this is the WMMA **B operand** (opIdx = 1) of a 64 (K) x 128 (N) tile, f16,
4 warps, warp size 32. #shared1's order = [1, 0] means that the N is the contiguous
dimension in LDS. WMMA wants K contiguous in registers, so the B operand needs to be transposed.

***** cvtLayout: the destination tensor's (register, lane, warp) -> LDS offset
      map, i.e. dstLayout^-1 . sharedLayout. This is the "wish list": where
      in LDS does every register of every lane of every warp want its data
      from.
cvtLayout:
 - register=1 -> (128)
   register=2 -> (256)
   register=4 -> (512)
   register=8 -> (2048)
   register=16 -> (4096)
   register=32 -> (32)
   register=64 -> (64)
 - lane=1 -> (1)
   lane=2 -> (2)
   lane=4 -> (4)
   lane=8 -> (8)
   lane=16 -> (1024)
 - warp=1 -> (16)
   warp=2 -> (0)
where out dims are: [offset (size 8192)]

Sanity check: 64*128 = 8192 elements, matches the offset out-dim size. Note
warp=2 -> (0): the WMMA ctaLayout's warp=2 basis is the *M*-warp component,
and the B operand doesn't depend on M, so half the warps redundantly read
the exact same LDS location as their sibling warp.

***** tile: what ds_load_tr16_b128 needs to be contiguous in LDS. For 16-bit
      types on gfx1250, instBitWidth = 128 bits = 8 halfwords, so
      tileSize = 8: 8 lanes must each hold one contiguous halfword,
      contributing 8 contiguous elements total.
tile:
 - lane=1 -> (1)
   lane=2 -> (2)
   lane=4 -> (4)
where out dims are: [offset (size 8)]

***** fullTile: the full geometry of *one* ds_load_tr16_b128 across all 32
      lanes of the wave. lane={1,2,4} are the "tile" lanes (contiguous
      offsets); register={1,2,4} lets one lane fetch further along the
      addr (non-contiguous) axis; lane={8,16} extends to the remaining
      lanes of the wave, also along addr. Warp contributes nothing (single
      instruction is issued independently per warp).
fullTile:
 - lane=1 -> (1, 0)
   lane=2 -> (2, 0)
   lane=4 -> (4, 0)
   lane=8 -> (0, 8)
   lane=16 -> (0, 16)
 - register=1 -> (0, 1)
   register=2 -> (0, 2)
   register=4 -> (0, 4)
 - warp is a size 1 dimension
where out dims are: [offset (size 8), addr (size 32)]

Sanity check: offset(8) x addr(32) = 256 halfwords moved by one wave-wide
instruction = 8 halfwords/lane x 32 lanes. Matches instBitWidth (128 bits =
8 halfwords) x warp size (32).

***** maybeQuot = divideLeft(cvtLayout, tile): divide the destination
      layout by the single-instruction tile. This is the L / T division
      from the linear-layout refresher: it's cvtLayout with the
      contiguous 8-element tile "factored out", leaving the repetition
      structure -- i.e. which *instruction* (not which element within it)
      each register/lane/warp belongs to.
maybeQuot:
 - register=1 -> (16)
   register=2 -> (32)
   register=4 -> (64)
   register=8 -> (256)
   register=16 -> (512)
   register=32 -> (4)
   register=64 -> (8)
 - lane=1 -> (1)
   lane=2 -> (128)
 - warp=1 -> (2)
   warp=2 -> (0)
where out dims are: [offset (size 1024)]

***** reps = zerosLike(tile) * maybeQuot: reinstate the tile's lane bases
      (zeroed, since within one instruction's tile all lanes still land on
      the *same* logical repetition) so reps' output offsets line back up
      with cvtLayout's full 8192-element space. The register dimension is
      untouched throughout -- tile/fullTile never reach into register bits
      beyond {1,2,4} (the 3 bits one instruction fills), so cvtLayout,
      maybeQuot and reps all have register size 128. reps is cvtLayout with
      only the tile's own 3 lane bits zeroed out; the leftover 4 register
      bits {8,16,32,64} are genuine repetitions -- 2^4 = 16 separate
      ds_load_tr16.b128 instructions, matching the 16 calls in the
      generated LLVM below.
reps:
 - register=1 -> (128)
   register=2 -> (256)
   register=4 -> (512)
   register=8 -> (2048)
   register=16 -> (4096)
   register=32 -> (32)
   register=64 -> (64)
 - lane=1 -> (0)
   lane=2 -> (0)
   lane=4 -> (0)
   lane=8 -> (8)
   lane=16 -> (1024)
 - warp=1 -> (16)
   warp=2 -> (0)
where out dims are: [offset (size 8192)]

***** fullTile.invert(): the inverse map, from (offset, addr) to
      (lane, register, warp). This tells you, for a given position *within*
      one instruction's tile (offset) and a given repetition of the
      instruction (addr), which lane/register the transposed result lands
      in. Because ds_load_tr16 transposes lanes, this is *not* the identity
      -- addr=8 and addr=16 map back onto *lane*, not register, since those
      addr bits came from extra lanes joining the cooperative load, while
      addr=1,2,4 map onto *register* since those came from one lane
      striding through its own registers.
fullTile.invert():
 - offset=1 -> (1, 0, 0)
   offset=2 -> (2, 0, 0)
   offset=4 -> (4, 0, 0)
 - addr=1 -> (0, 1, 0)
   addr=2 -> (0, 2, 0)
   addr=4 -> (0, 4, 0)
   addr=8 -> (8, 0, 0)
   addr=16 -> (16, 0, 0)
where out dims are: [lane (size 32), register (size 8), warp (size 1)]

***** addrToOffset = fullTile.invert().compose(reps): for each (offset,
      addr) pair -- i.e. each element position within an instruction's
      tile, for each repetition of the instruction -- the real LDS byte
      offset to touch. Composing through reps substitutes the "which
      repetition" (addr) for the *actual* runtime offset that repetition
      corresponds to in the 8192-element tensor.
addrToOffset:
 - offset=1 -> (0)
   offset=2 -> (0)
   offset=4 -> (0)
 - addr=1 -> (128)
   addr=2 -> (256)
   addr=4 -> (512)
   addr=8 -> (8)
   addr=16 -> (1024)
where out dims are: [offset (size 8192)]

Note offset={1,2,4} -> 0: these are the tile-internal positions, they don't
change *which* LDS location to read from (ds_load_tr16 reads one 128-bit
chunk per lane regardless), only the addr bases matter for choosing where
that chunk is.

***** addrLayout: addrToOffset's addr bases, relabelled as lane bases (plus
      reps' warp bases). This is the payoff: the hardware instruction
      shuffles data across lanes, so the *lane issuing the load* is not the
      lane that ends up owning the data (that's what fullTile.invert()
      already told us). Renaming addr -> lane lets the lowering plug the
      *runtime* laneId straight in and get the LDS address that particular
      lane must issue its load from.
addrLayout:
 - lane=1 -> (128)
   lane=2 -> (256)
   lane=4 -> (512)
   lane=8 -> (8)
   lane=16 -> (1024)
 - warp=1 -> (16)
   warp=2 -> (0)
where out dims are: [offset (size 8192)]

Full lowering emits exactly 16 ds.load.tr16.b128 calls (128 dst registers /
8 elements-per-instruction = 16), matching cvtLayout's register in-dim size
divided by fullTile's register+tile contribution.
